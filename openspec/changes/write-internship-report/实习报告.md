## 一、实习目的

### 1.1 学术研究目标

本次实习的核心学术目标是深入研究加密流量分类技术领域的前沿问题，特别是在开放集识别和增量学习两个关键技术方向上实现突破性进展，最终形成高质量的学术成果。

#### 1.1.1 探索开放集识别在加密流量分类中的应用

传统的流量分类方法通常采用封闭集假设，即假设测试集中的所有类别在训练阶段都已出现。然而，这一假设在实际网络环境中完全失效。随着移动互联网、物联网的快速发展，新的应用程序和通信协议层出不穷，流量类型始终处于动态变化之中。据统计，每年新出现的移动应用数量以百万计，每个应用都可能产生独特的流量模式。

开放集识别的核心挑战在于：如何让模型在训练时没有见过某个类别的情况下，能够正确地将测试集中属于该类别的样本识别为"未知"，而不是错误地将其归类为某个已知类别。这在网络安全监控、异常检测、入侵检测等应用场景中具有至关重要的意义。例如，当网络中出现一种新型的恶意软件或攻击流量时，安全系统需要能够第一时间识别出这是"未知"的威胁，而不是将其误判为正常的已知流量。

本研究旨在探索和验证有效的开放集识别方法，使加密流量分类系统能够：
- 准确检测训练阶段未见过的流量类别
- 提供可靠的置信度估计，区分"确定已知"和"可能未知"的样本
- 在保持对已知类高识别率的前提下，降低对未知类的误判率

#### 1.1.2 解决数据不均衡条件下的分类性能问题

真实网络环境中的流量分布呈现极端的不均衡特征。根据Cisco的全球流量报告，视频流媒体、文件传输等主流应用的流量占据了网络总流量的80%以上，而即时通讯、邮件服务等小众应用的流量占比不足5%。这种严重的类别不均衡给传统的机器学习模型带来了巨大挑战。

在标准训练流程中，模型会被多数类样本主导，学习到的决策边界会严重偏向多数类，导致对少数类的识别能力大幅下降。在本研究使用的数据集中，虽然总体准确率达到96%，但对于某些少数类（如VPN: Chat和VPN: Email），模型的F1分数竟然为0，这意味着模型完全无法识别这些类别。

这种性能在实际应用中是不可接受的，原因在于：
1. **少数类往往承载重要业务**：企业内部的关键业务系统、专用的通讯工具等，虽然流量量不大，但业务重要性极高
2. **安全威胁常伪装成少数类**：恶意流量往往会模仿或嵌入到正常的小众应用流量中
3. **长期性能下降**：随着时间推移，少数类样本不断累积，但模型无法识别，会导致系统整体性能恶化

本研究的目标是在不牺牲多数类性能的前提下，显著提升对少数类的识别能力，探索在不均衡数据分布下的有效学习策略。

#### 1.1.3 实现增量式学习能力

增量学习是指模型在已有知识的基础上，能够学习新类别的数据，而不需要从头重新训练整个模型。这对于构建可扩展、可维护的智能网络管理系统至关重要。

在实际部署场景中，流量分类系统面临以下挑战：
- **新应用持续涌现**：每周都有新的移动应用上线，产生新的流量模式
- **用户行为变化**：流行应用的使用模式会随时间演变
- **协议升级迭代**：现有协议会升级，新协议会被引入

传统的解决方法是每当出现新类别时，就重新收集包含所有类别的数据集，从头训练一个新的模型。这种方法存在严重问题：
1. **计算成本高昂**：每次重新训练需要消耗大量的计算资源和时间
2. **历史数据难以获取**：早期类别的原始流量数据可能已经丢失或不可用
3. **灾难性遗忘**：神经网络在学习新知识时，往往会严重遗忘旧知识

本研究旨在探索有效的增量学习框架，使系统能够：
- 在保留对已有类别识别能力的前提下，添加对新类别的识别
- 仅需少量新类别的样本即可完成学习（Few-Shot Learning）
- 避免或减轻灾难性遗忘问题
- 保持模型的紧凑性和推理效率

## 二、实习内容

### 2.1 研究背景与技术现状

#### 2.1.1 加密流量分类的挑战

随着网络安全意识的提升和网络加密技术的普及，HTTPS、VPN、Tor等加密协议在网络流量中的占比持续增长。根据Google的统计，全球超过90%的网页浏览使用HTTPS加密。传统的基于深度包检测的流量分类方法，因无法解析加密载荷而逐渐失效。

在此背景下，基于机器学习和深度学习的流量分类方法成为研究热点。Deep-Packet作为一种基于ResNet1d的深度学习方法，在ISCX VPN-nonVPN 2016数据集上展现了优异的性能，整体准确率可达96%以上。然而，通过深入的实验分析，我们发现该基准模型在实际应用场景中仍存在三个致命问题：

**问题一：开放集识别能力缺失**

基准模型采用标准的Softmax层进行分类输出。在开放集场景下，当模型遇到训练阶段未见过的流量类别时，Softmax层仍然会对所有输出类别进行归一化，产生一个看似"确定"的预测。实验结果表明，模型对于未见过的大规模流量类别（如P2P、VoIP），不是将其识别为"未知"，而是以超过80%的置信度错误地将其归类为某个已知类别。

这种行为的危险性在于：在实际网络管理中，运营者无法判断哪些预测是可靠的，哪些可能是错误的。当系统以高置信度做出错误预测时，会导致严重的误判和决策失误。

**问题二：数据不均衡导致少数类识别失败**

ISCX VPN-nonVPN 2016数据集包含6个流量类别，样本量从几十到几千不等。虽然基准模型在多数类（如Streaming、VoIP）上的F1分数超过0.98，但对于样本量极少的少数类（如Chat的215个样本、Email的65个样本），模型的F1分数为0。

通过混淆矩阵分析发现，模型将所有少数类样本都错误地预测为多数类。这说明模型的决策边界被多数类样本完全主导，少数类的特征空间被"挤占"殆尽。

**问题三：增量学习能力不足**

当需要识别新的流量类型时，传统方法需要重新收集包含所有类别（旧类别+新类别）的完整数据集，从头训练一个新的模型。这不仅计算成本高昂（每次训练需要数小时到数天），而且往往面临"灾难性遗忘"问题——在学习新类别时，模型对旧类别的识别能力会显著下降。

#### 2.1.2 初步技术探索与挫折

在研究初期（2025年10月），我们尝试了多种主流的改进方案，但均未取得预期效果：

**尝试一：引入SEBlock注意力机制**

SEBlock（Squeeze-and-Excitation Block）是一种通过自适应地重新校准通道特征响应来提升模型性能的注意力机制，在ImageNet等图像分类任务中取得了显著效果。我们在ResNet模型的每个残差块后引入SEBlock，期望模型能够自动学习到不同特征通道的重要性。

然而，实验结果令人失望：整体准确率从96.3%下降到95.1%，宏平均F1从0.72骤降至0.52。通过深入分析发现，SEBlock在流量序列数据上的表现远不如在图像数据上。原因可能在于：流量数据的通道维度（packet的不同字节位置）不具备图像通道（RGB颜色通道）那样的语义一致性，SEBlock难以学到有意义的注意力权重。

**尝试二：SMOTE数据增强**

SMOTE是一种流行的合成少数类过采样技术，通过在特征空间中对少数类样本进行插值来生成新的训练样本。我们对Chat和Email这两个少数类应用SMOTE，将它们的样本量增加到与多数类相当的水平。

结果却是一次彻底的失败：模型严重过拟合，宏平均F1分数从0.72骤降至0.31。测试集上，模型将几乎所有样本都预测为少数类。分析发现，SMOTE生成的"合成流量样本"在序列数据上完全不合理。流量序列具有严格的时序结构和协议约束，简单的线性插值会破坏这些结构，产生"物理上不可能"的样本。

**尝试三：Focal Loss损失函数**

Focal Loss通过降低易分类样本的权重，使模型更专注于难分类样本，在目标检测等领域取得了成功。我们希望通过Focal Loss强制模型关注那些"难以区分"的少数类样本。

实验结果更加灾难性：宏平均F1分数仅为0.09，模型几乎完全失去分类能力。深入分析发现，在极度不均衡的数据分布下（多数类比少数类多100倍），Focal Loss的动态权重调整机制反而加剧了不稳定性。模型在训练过程中陷入"少数类样本损失极小→梯度极小→权重更新几乎为零"的恶性循环。

**尝试四：简单MoE架构**

这是唯一取得部分成功的尝试。我们训练了一个专门的少数类专家模型，然后将其与基准模型的预测结果进行简单加权平均（权重通过网格搜索确定为0.15）。

虽然总体准确率从90.8%下降到87.2%，但宏平均F1从0.72提升到0.78。更重要的是，少数类的F1从0提升到了0.11-0.14，证明了专家模型路线的可行性。然而，固定权重的简单平均显然不是最优方案，我们需要一个更智能的融合机制。

这些初步实验虽然没有取得突破性进展，但为后续研究提供了重要的方向指引：
1. 避免在流量数据上盲目应用图像领域的方法
2. 数据增强需要考虑数据的特殊结构
3. 损失函数的调整需要谨慎，特别是在极端不均衡情况下
4. 专家模型路线值得深入探索

### 2.2 数据集净化与预处理

#### 2.2.1 数据污染问题的发现

在深入研究过程中（2025年10月24-25日），我们意识到数据集的"纯净度"对模型性能评估至关重要。通过使用tcpdump、Wireshark等工具分析原始的ISCX VPN-nonVPN 2016数据集，我们发现了多个严重的信息泄露问题：

**IP地址的明文泄露**

通过`tcpdump -X`命令分析数据包内容，我们发现IP地址以明文形式存在。虽然IP头在加密流量中本身不加密（因为路由需要），但模型可能学习到"特定IP地址段对应特定应用"的错误关联。例如，如果某个视频流媒体服务使用固定的IP地址段，模型会直接记忆这个关联，而不是学习流量本身的特征。这种关联在实际环境中是完全不可靠的，因为IP地址会变化、会复用。

**端口号的明文泄露**

与IP地址类似，端口号也是明文的。许多应用使用默认端口（如HTTP的80、HTTPS的443），模型可能直接记忆"端口443 = HTTPS流量"，而不是学习载荷特征。同样，这在实际应用中是不可靠的，因为许多应用使用非标准端口，或者通过端口复用技术共享端口。

**基础设施协议的噪声干扰**

通过分析发现，数据集中存在大量与目标应用流量无关的基础设施协议数据包：
- ARP（Address Resolution Protocol）：地址解析协议，用于将IP地址映射到MAC地址
- DNS（Domain Name System）：域名系统，用于域名解析
- NTP（Network Time Protocol）：网络时间协议，用于时间同步
- NBNS（NetBIOS Name Service）：NetBIOS名称服务
- LLMNR（Link-Local Multicast Name Resolution）：链路本地多播名称解析

这些协议具有极强的模式特征（如DNS查询总是包含特定的查询格式和响应格式），会对模型学习造成严重干扰。模型可能会"走捷径"，直接识别这些基础设施协议的特征，而不是学习目标应用的流量模式。

**VPN/Tor与Non-VPN数据集的纯净度差异**

通过对比分析发现，VPN和Tor数据集由于隧道封装机制，天然地过滤掉了大部分基础设施协议。当应用流量通过VPN或Tor隧道传输时，外部观察者看到的是统一的VPN/Tor协议包，原始的ARP、DNS等协议被封装在隧道内部，不可见。

这一发现为后续实验的数据选择提供了重要参考：**优先使用VPN和Tor数据集可以规避大部分数据污染问题**。Non-VPN数据集虽然包含更多样化的应用类型，但其纯净度较差，需要更严格的预处理。

#### 2.2.2 预处理流程的强化

针对上述问题，我们对数据预处理流程进行了系统性增强：

**IP地址混淆**

在`preprocessing.py`中实现了`mask_ip`函数，将IP地址的四个字节全部置零。具体实现如下：
- 解析IP头，提取源IP和目的IP
- 将IP地址的四个字节全部设置为0
- 重新计算IP校验和（因为IP头内容变化了）

这样处理后的数据包，IP地址部分不再包含任何可辨识的信息，模型无法通过IP地址进行"作弊"。

**端口混淆**

我们实现了`mask_ports_to_zero`函数，将源端口和目的端口都设置为0。与IP混淆类似，这需要重新计算传输层（TCP/UDP）的校验和。

为了保持灵活性，我们添加了`--mask-ports`命令行参数。在某些特殊场景下（如研究端口号对分类的影响），可以选择不混淆端口。

**基础设施协议过滤**

这是净化工作的关键一步。我们在`utils.py`中实现了`should_omit_packet`函数，在预处理的最早阶段（读取PCAP文件时）就丢弃无关协议的数据包。

**数据集生成脚本的改进**

我们修复并增强了`create_train_test_set.py`脚本：
1. **修复文件加载Bug**：将文件匹配模式从`/*.json.gz`改为`/**/*.json.gz`，支持递归查找分块文件
2. **新增实验类型**：添加`--experiment_type imbalanced`选项，保留数据的原始分布，不进行欠采样
3. **完善文档**：在脚本顶部添加详细注释，说明每种实验类型的具体行为

#### 2.2.3 少数类的确定与专家数据集构建

通过分析净化后的VPN流量数据的`traffic_label`分布，我们确定了少数类：

**类别分布统计**
```
类别5 (VPN: Chat):      215个样本
类别6 (VPN: File Transfer): 1,034个样本
类别7 (VPN: Email):     65个样本
类别8 (VPN: P2P):       4,408个样本
类别9 (VPN: Streaming): 1,089个样本
类别10 (VPN: VoIP):     9,476个样本
```

从统计可以看出，类别5和7的样本量明显少于其他类别（特别是类别10，是其150倍以上）。因此，我们确定类别5（VPN: Chat）和7（VPN: Email）为少数类。

为了构建少数类专家数据集，我们重构了`create_train_test_set.py`脚本，增加了`--minority-classes`参数，允许动态指定少数类标签。

### 2.3 门控专家集成（GEE）框架的设计与实现

#### 2.3.1 框架设计理念

基于前期的探索和发现，我们提出了**Gated Expert Ensemble (GEE)**框架。其核心思想是通过多个专门化子模型的协作来解决复杂问题。

**专家模型的分工**

- **基准模型**：在完整数据集（包含所有类别）上训练，对多数类识别能力强，作为"通用专家"
- **少数类专家模型**：仅在少数类数据集上训练，专门学习少数类的细微特征，作为"专项专家"

这种分工的优势在于：基准模型不需要为了照顾少数类而牺牲多数类的性能，少数类专家可以专注于少数类的特征学习，形成优势互补。

**可学习的门控机制**

我们设计了一个多层感知机作为门控网络，其输入是两个专家模型的预测概率向量，输出是融合后的预测结果。

门控网络的工作原理：
1. 接收基准模型和专家模型的N维概率向量（N为类别数），拼接成2N维输入
2. 通过两层全连接层（隐藏层使用ReLU激活）进行非线性变换
3. 输出N维logits，经Softmax归一化后得到最终预测

与简单的加权平均不同，门控网络能够根据输入样本的特征，动态决定信任哪个专家。例如，对于明显属于多数类的样本，门控网络可能学会"完全信任基准模型"；对于模棱两可的样本，可能"两者结合"；对于明显的少数类样本，可能"主要信任专家模型"。

**解决类别不均衡的训练策略**

在门控网络的训练中，我们采用了加权交叉熵损失。这种策略为少数类样本赋予更高的损失权重，强制门控网络关注少数类的识别。

#### 2.3.2 门控网络的实现细节

**网络架构**

门控网络采用多层感知机结构，包含输入层、两个隐藏层和输出层。使用ReLU激活函数和Dropout正则化。

**训练流程**

门控网络的训练分为三个步骤：
1. **冻结专家模型**：加载预训练的基准模型和少数类专家模型，冻结参数
2. **生成训练数据**：将训练集样本送入两个专家模型，获取预测概率
3. **训练门控网络**：使用加权交叉熵损失训练门控网络

**关键教训：数据泄露的发现与修正**

在初期实现中，我们犯了一个严重的方法论错误：直接使用测试集来训练门控网络。这是一个典型的数据泄露错误。在导师的指正下，我们立刻修正了该流程，建立了严格的训练/评估分离。

#### 2.3.3 实验结果与分析

在净化后的VPN流量数据集上，GEE框架取得了显著的成果：

**性能对比表**

| 模型 | 整体准确率 | 宏平均F1 | 类别5 F1 (Chat) | 类别7 F1 (Email) |
|------|-----------|----------|----------------|----------------|
| 基准ResNet | 96.33% | 0.63 | 0.00 | 0.00 |
| 简单加权 (0.15) | 96.41% | 0.67 | 0.11 | 0.14 |
| **GEE框架** | **95.00%** | **0.83** | **0.28** | **0.92** |

**关键发现与分析**

1. **宏平均F1大幅提升**：从0.63提升到0.83（提升31.7%），说明模型在各类别上的均衡性能显著改善

2. **少数类识别能力突破**：基准模型完全无法识别少数类（F1=0），GEE框架将类别5的F1提升到0.28，类别7提升到0.92

3. **整体准确率的合理牺牲**：GEE框架的整体准确率从96.33%下降到95.00%，下降了1.33个百分点。这是一个合理的代价

### 2.4 开放集识别能力的突破

#### 2.4.1 基线模型的开放集性能评估

为了定量评估开放集识别能力，我们设计了严格的6折交叉验证实验（2025年11月22日）。

**基线模型的糟糕表现**

实验结果揭示了基线模型的严重缺陷：

| 排除类 | AUROC | FPR@TPR95 | 整体准确率 |
|--------|-------|-----------|-----------|
| 类别5 | 0.9385 | 0.2727 | 94.12% |
| 类别6 | 0.9737 | 0.0208 | 96.85% |
| 类别7 | 0.9746 | 0.0909 | 96.23% |
| 类别8 | 0.8692 | 0.9742 | 87.35% |
| 类别9 | 0.9420 | 0.8266 | 91.47% |
| 类别10 | 0.9511 | 0.6682 | 92.58% |
| **平均** | **0.9415** | **0.4756** | **93.10%** |

**核心问题诊断**

1. **性能极不稳定**：模型的表现完全取决于哪个类别被排除
2. **多数类导致灾难性失败**：当类别8或10作为未知类时，FPR@TPR95超过0.8-0.97
3. **类别6成为"黑洞"**：当类别8或10被排除时，模型将大量未知样本误判为类别6

#### 2.4.2 "垃圾类别"策略的提出与实现

针对基线模型的问题，我们提出了**"垃圾类别"（Garbage Class）**策略（2025年12月6日）。

**核心思想**

在开放集识别中，传统做法是训练一个N类模型，然后通过Softmax置信度判断是否为未知。"垃圾类别"策略的反向思考是：为什么不让模型在训练时就明确地看到"未知样本"是什么样的？

我们训练一个N+1类的模型，其中前N个类是已知类，第N+1个类是"垃圾类"（Garbage Class）。训练时，我们从完整数据集中选择一个或多个类别作为"垃圾"，告诉模型"这些是未知类的例子"。

**技术实现**

1. **数据准备**：使用`create_train_test_set.py --experiment_type select_classes --select_classes 8`，仅选择类别8的数据作为"垃圾数据"

2. **模型修改**：在`ml/model.py`中修改`GatingNetwork`，增加`use_garbage_class`参数，输出维度动态调整为N+1

3. **训练修改**：在`train_gating_network.py`中支持`--use-garbage-class`和`--unknown-class-data-path`参数

4. **评估修改**：在`evaluation.py`中增加`--gating-has-garbage-class`标志，置信度计算逻辑切换为"1 - 垃圾类的概率"

#### 2.4.3 开放集识别的突破性成果

"垃圾类别"策略取得了巨大成功！实验结果对比如下：

| 排除类 | 指标 | 基准模型 | GEE (垃圾类) | 提升 |
|--------|------|----------|-------------|------|
| **类别7** | FPR@TPR95 | 0.0909 | 0.0323 | **-58.6%** |
| **类别8** | FPR@TPR95 | 0.9742 | 0.0246 | **-94.9%** |
| **类别9** | FPR@TPR95 | 0.8266 | 0.0127 | **-81.4%** |
| **类别10** | FPR@TPR95 | 0.6682 | 0.0254 | **-64.3%** |

**核心结论**

1. **FPR@TPR95的巨大改善**：在基准模型表现最差的场景（排除类别8、9、10），GEE将FPR@TPR95从0.8-0.97的灾难性水平降低到0.01-0.03的优秀水平

2. **性能的一致性提升**：除类别6略有下降外，GEE在所有其他类别上都取得了性能提升或保持

在6折交叉验证实验中，GEE框架在开放集识别任务上取得了显著的性能提升。当多数类（类别8、9、10）作为未知类时，GEE框架的性能提升最为显著：
- 类别8（P2P）：FPR@TPR95提升97.5%
- 类别9（Streaming）：FPR@TPR95提升98.5%
- 类别10（VoIP）：FPR@TPR95提升96.2%

#### 4.1.3 证明了框架的通用性和可迁移性

通过在CNN基线模型上的验证，证明了GEE架构不依赖于特定的基线模型。CNN-GEE在开放集识别任务上也取得了一致的性能提升，特别是在类别7的测试中达到了完美的开放集识别效果（FPR@TPR95 = 0）。
